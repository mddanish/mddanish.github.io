PHP2SHELL

Two memory-safety bugs in the PHP interpreter's request lifecycle. Both let an unauthenticated attacker reach remote code execution with the web worker's privileges — the out-of-memory path (…618) before your application code even runs, and the stale-state path (…619) by reusing a worker across requests.

How each bug works

Both are classic memory-safety faults, reached through ordinary request handling. The mechanism below is conceptual — enough to understand reachability and impact, not a recipe.

Class
Memory corruption (heap)
Trigger
Allocation failure while per-request data is only partly initialized
Attack vector
Network, unauthenticated. Crafted multipart requests can exhaust memory while appearing within configured limits.
Impact
RCE as the web worker; confirmed from PHP 5.4.0 onward
Highest risk
mod_php — fault reachable before app code
Where it goes wrong
1
Request arrives. PHP begins allocating internal structures for the request body.
2
Memory runs out. An allocation fails mid-way, leaving request data half-initialized.
3
Cleanup runs anyway. The teardown path treats the incomplete structures as if fully valid — reading and freeing fields that were never set up.
4
Corruption. Operating on that invalid state corrupts the heap, which an attacker who controls the layout can steer toward code execution.
Why limits don't save you: RLIMIT_AS / RLIMIT_DATA can actually trigger the vulnerable path. Container and cgroup caps help availability but are not a complete fix.
Known OOM shapes: public research demonstrates oversized multipart fields, header amplification across many parts, and deeply nested empty-file controls. They are useful detection signals, not a substitute for patching.
Class
Use-after-free (cross-request)
Trigger
Leftover global state references memory freed at the end of an earlier request
Confirmed paths
Session upload-progress (on by default); fatal-error backtraces (PHP 8.5)
Attack vector
Network, unauthenticated. Worker reuse + an interrupted cleanup (fatal error or timeout).
Impact
RCE as the web worker; memory disclosure also confirmed
Affected models
Both mod_php and PHP-FPM
Where it goes wrong
1
Request A runs on a pooled worker and leaves some global state behind.
2
Cleanup is interrupted by a fatal error or timeout, so the normal reset never fully clears that state.
3
Memory is freed but a stale global pointer still refers to it. The worker stays alive for reuse.
4
Request B lands on the same worker and touches the stale pointer before init clears it — using freed memory an attacker can have reallocated.
Silence is not safety: suppressing diagnostics (error_reporting, display_errors, @) does not stop stale-state access. Absent log entries do not prove an installation is safe.
The five exploit chains

Public analysis maps the two CVEs to five concrete chains — one OOM path (…618) and four stale-state paths (…619). Each has a different precondition and runtime surface.

Fix & mitigations

Updating is the only complete remediation for both flaws. Temporary mitigations reduce exposure but do not remove the underlying fault — and every config change needs a full worker restart to take effect.

Detection notes

  • Public PoCs exist. Working proof-of-concept code is published by multiple researchers, and in-the-wild attempts are confirmed.
  • Watch for multipart POSTs with unusually many fields or headers, large bodies, repeated out-of-memory / HTTP 500 responses, and Apache child crashes or restarts.
  • Grep logs for zend_mm_heap corrupted and Allowed memory size … exhausted in Unknown on line 0 — evidence the failure happened before application code.
  • For …619, correlate fatal errors / timeouts immediately followed by unusual behavior on the same worker.
  • Treat absence of error-log entries as inconclusive — the stale-state path leaves no required trace.
  • A focused edge control is to block PHP_SESSION_UPLOAD_PROGRESS in multipart bodies. Reference Suricata, Sigma, ModSecurity, and Lua detections are available with the ikow PoC research.
  • Inventory every PHP install, including bundled/embedded ones behind appliances and containers.
Confirm your exact build after updating: php -v on CLI reflects the CLI SAPI; verify the web SAPI (mod_php / FPM) separately, then restart all workers.

Detection rules

Behavioral starting points, built from the confirmed mechanism — not signatures of any one exploit. Both flaws corrupt memory, so the strongest signal is host-side: worker crashes and respawns, not a clean network payload. Treat these as illustrative and tune to your stack.

SIEMSigma · host/app logs · strongest signal 
# php-fpm / apache mod_php worker crash + UAF indicators
title: PHP2SHELL worker crash indicators
logsource:
  product: linux
  service: php-fpm        # also apache error_log for mod_php
detection:
  crash:
    message|contains:
      - 'exited on signal 11'    # SIGSEGV
      - 'exited on signal 6'     # SIGABRT
      - 'zend_mm_heap corrupted'
      - 'out of memory'
  interrupted:               # CVE-2026-109619 precondition
    message|contains:
      - 'Fatal error'
      - 'Maximum execution time'
  timeframe: 2m
  condition: crash or ( interrupted and crash )
falsepositives:
  - Legitimate OOM under load
  - Segfaults from unrelated extensions
level: high
IDSSuricata · network heuristic 
# Burst of multipart POSTs from one source (CVE-2026-109618 surface)
alert http any any -> $HTTP_SERVERS any ( \
  msg:"PHP2SHELL possible OOM probe: multipart POST burst"; \
  flow:to_server,established; \
  http.method; content:"POST"; \
  http.header; content:"multipart/form-data"; nocase; \
  threshold: type both, track by_src, count 20, seconds 10; \
  sid:2026109618; rev:1; )
WAFModSecurity · request-shape heuristic 
# Flag abnormal multipart bodies; tune thresholds per app. Reduces exposure, not a fix.
SecRule REQUEST_METHOD "@streq POST" \
  "id:2026109618,phase:2,log,pass,msg:'PHP2SHELL: inspect multipart shape',chain"
  SecRule REQUEST_HEADERS:Content-Type "@rx multipart/form-data" "chain"
    SecRule &FILES "@gt 200"        # unusually high part count — set to your real ceiling

# Also block the stale-state trigger name in multipart bodies:
SecRule MULTIPART_PART_HEADERS "@rx PHP_SESSION_UPLOAD_PROGRESS" \
  "id:2026109619,phase:2,log,pass,msg:'PHP2SHELL: upload-progress field present'"
Before you trust any rule: validate against your own traffic, watch false positives (crashes and large uploads happen for benign reasons), and remember these catch known patterns, not all variants. Absence of alerts does not prove safety — the …619 path can leave no required trace. Pre-built rule sets (e.g. the ikow PoC detection/ — Suricata, Sigma, ModSecurity, Lua) are useful to compare against, but review every rule before deploying it.
